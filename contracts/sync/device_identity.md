# AtlasVault Device Identity Contract

This contract defines the Phase 2F-1 installation identity structures. It does
not establish trust, link a device, transport a vault key, or define a server
registry.

## Canonical Encoding

Objects use UTF-8 JSON with keys sorted lexicographically and no insignificant
whitespace. Decoders reject unknown or missing keys, non-canonical Base64,
Boolean values where integers are required, and timestamps other than strict
UTC seconds (`YYYY-MM-DDTHH:MM:SSZ`). Canonicalization determines the unsigned
bytes being signed and the signed-envelope bytes once a signature is supplied.
The protocol requires a valid Ed25519 signature, not deterministic signature
generation by every platform API.

## Public Descriptor

The descriptor has exactly seven keys:

```json
{
  "format": "atlasvault-device-descriptor",
  "version": 1,
  "device_id": "avd1-<64 lowercase hex>",
  "signing_public_key": "<canonical Base64 for 32 bytes>",
  "agreement_public_key": "<canonical Base64 for 32 bytes>",
  "created_at": "<strict UTC-seconds timestamp>",
  "key_epoch": 1
}
```

`version` is the integer `1`; `key_epoch` is a positive integer. The signing
key is an Ed25519 public key and the agreement key is an X25519 public key.
They are distinct key-usage roles even if generated at the same time.

The descriptor contains no private key, device or user label, platform, OS
version, device model, account ID, email, vault ID, or unknown field.

## Device ID

The device ID is recomputed during every decode and verification:

```text
"avd1-" + lowercase_hex(
  SHA-256(
    UTF8("atlasvault-device-id-v1:") ||
    signing_public_key_bytes ||
    agreement_public_key_bytes
  )
)
```

The key order is normative. An uppercase digest, wrong prefix or length,
caller-supplied mismatch, or alternate key order is invalid.

## Signed Descriptor

The signed envelope has exactly four keys:

```json
{
  "format": "atlasvault-signed-device-descriptor",
  "version": 1,
  "descriptor": {},
  "signature": "<canonical Base64 for 64 bytes>"
}
```

The Ed25519 signature input is:

```text
UTF8("atlasvault-device-descriptor-signature-v1:") ||
canonical_json(descriptor)
```

Verification first strictly validates the descriptor and recomputes its device
ID, then verifies the exact 64-byte signature with the descriptor signing key.
No alternate signature algorithm is accepted.

A valid self-signature proves possession of the matching private signing key.
It does not prove that the device should be trusted.

## Signature Generation Compatibility

The checked-in test vector contains fixed signatures generated by the Python
reference implementation. Every runtime must decode, preserve, and verify
those exact signed-envelope bytes. CryptoKit may generate another valid
Ed25519 signature for the same key and message because its signing API
intentionally randomizes generation. Such a signature is interoperable when
it is exactly 64 bytes and verifies over the canonical payload. No participant
may replace or normalize received signature bytes.

## Device-Identity Secret Bundle

The local secret bundle has exactly seven keys:

```json
{
  "format": "atlasvault-device-identity-secret",
  "version": 1,
  "device_id": "avd1-<64 lowercase hex>",
  "created_at": "<strict UTC-seconds timestamp>",
  "key_epoch": 1,
  "signing_private_key": "<canonical Base64 for a 32-byte Ed25519 seed>",
  "agreement_private_key": "<canonical Base64 for a 32-byte X25519 key>"
}
```

The bundle contains no duplicated public keys, platform metadata, label, vault
ID, or account ID. On load, the implementation strictly decodes the bundle,
reconstructs both private keys, derives both public keys, recomputes the device
ID, and requires an exact match before exposing the verified public identity.

The bundle is installation-local secret state. It is never exported,
synchronized, included in pairing messages, written to public cache, logged,
or included in error descriptions. Only clearly marked fake vector material
may appear in repository test data.

## Deferred Trust

Phase 2F-1 defines possession proofs and local custody only. Explicit trust
commitment, durable replay state, pairing transport, vault-key delivery,
revocation, and rotation require later separately reviewed phases.
